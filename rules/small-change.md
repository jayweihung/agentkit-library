# 改程式：最小又完整的改動

（重點取自 ponytail skill。要完整版、或要它更嚴格，叫 `/ponytail`。）

- 動手前先讀要改的程式，列出改動一定會碰到的地方：呼叫它的、測試、設定、匯出。這就是範圍；沒人要的功能不算。
- 照順序，選第一個能完整解決的：不做也可以嗎 → 這個專案已經有的 → 標準函式庫或平台本身有的 → 已經裝的套件 → 一行看得懂的寫法 → 最後才自己寫，而且寫最少。
- 不加沒人要的抽象、包裝、選項、設定、「以後可能用到」的程式。能刪就不要加。照專案原本的結構和慣例。
- 懶在解法，不懶在做完：改動弄壞的呼叫端、測試、設定都要一起改好。修 bug 先找出所有呼叫端，在共用的地方修根本原因，只修一次。
- 大小差不多的寫法，選邊界情況也對的那個。
- 不能省：信任邊界的檢查、防止資料遺失的錯誤處理、安全、使用者明確要的東西。
- 想多做的（多一個提示的地方、多一個按鈕、多一個選項），用一行說出來讓使用者決定，不要直接做。
- 做完用一兩行說：省掉了什麼、沒檢查什麼、使用者需要知道的風險。
